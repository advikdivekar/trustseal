# Decisions

- **Folder:** code lives directly in `dccustomer/` (`api/`, `web/`), no `trustseal/` subfolder.
- **Stack:** FastAPI + SQLite (stdlib sqlite3) and Vite + React + TypeScript + `motion`, matching CertifyAI. No Docker, Redis or Postgres yet.
- **Ports:** API 8010, web 3011 (8000 and 3001 belong to CertifyAI).
- **Ledger:** hash-linked, server-signed, append-only via SQLite triggers. Tamper-evident, not a blockchain. A whole-DB rewrite by the admin is not prevented; device signatures and external anchoring are the planned answer.
- **Stage locking is enforced in the API** (403 wrong role, 409 locked/not started/not ready), never only in the UI.
- **AI is open-source only.** Milestone 1-4 uses deterministic mock checks so the demo cannot fail on a model. Planned: OpenCV (quality, QR, seal compare), DINOv2-small or OpenCLIP (product match), CIELAB + ΔE2000 with the label's colour strip (colour), PaddleOCR or EasyOCR (serials), imagehash (reuse). Thresholds in one YAML. AI flags, humans decide.
- **Seal ID mismatch is deterministic**, no ML. **The seal is read from the parcel, never issued by the system** (a seller cannot be handed a code by the platform: the sticker comes from a supplier with its serial already printed). The serial is read with zxing then OCR and bound to the parcel on first scan; one serial can only ever bind once. The shared record keeps its SHA-256 and the last three characters, never the serial, so a message or the ledger cannot be used to fake a scan. The honest limit: someone who can see the physical sticker can read it too, which is why the seal is one signal among several (packing video, photos, the unboxing barcode).
- **One live channel:** every phone follows the newest shipment over a single WebSocket; the server broadcasts a full snapshot after each commit and clients refetch on reconnect.
- **Design:** H&M-style retail look (Inter, square corners, uppercase labels, order stepper), cream paper and one indigo ink, vermilion only for failure. The chain of custody is a delivery route (shop, warehouse, van, door, home), one road segment per stage. An earlier Japanese woodblock bridge was removed at the user's request.
- **People and devices:** named accounts with PINs; one device is one person and an account lives on one device. Rehearsal mode (presenter toggle) keeps sessions per tab so one laptop can play all four.
- **Product recognition:** the seller shows the product to the camera; local gemma3:4b via Ollama returns brand, name, size and colours, the seller can edit, and the confirmed identity is part of the ledger. The buyer's check compares the received photo with that reference (CIEDE2000 colour + vision model). A model alone never fails a parcel with low confidence: uncertain goes to REVIEW.
- **Barcode is identity.** The product's own barcode/ISBN is read deterministically (zxing-cpp) and must match exactly at the buyer. The vision model only describes the product; it never invents a barcode or a size (sizes that do not look like a weight or volume are dropped).
- **A barcode is only trusted if the camera read it and it belongs to the product shown.** Typed numbers are refused; the server remembers what it read keyed by the photo hash and ignores what a phone sends. The code is looked up in public catalogues and the name must agree with the front photo (token overlap), otherwise registration is refused; an unknown code is flagged "unverified". Offline, everything is "unverified" rather than silently trusted.
- **Pay at the door against the seal, check the product at home.** The door proves the parcel is the one packed and unopened; opening it in front of a courier is not realistic. Product fraud is caught by the home scan, which files the complaint automatically. The seller is paid at the door and the complaint claws it back, so a wrong item costs the seller, not the buyer.
- **Automatic refunds only on strong, independent evidence and a ceiling** (₹5,000): barcode differs AND the look differs AND seals intact AND record intact AND the packing video does not show the registered barcode. Anything contradictory goes to a person, because a buyer could scan a different product on purpose.
- **Packing video** is required evidence for the seller. It is analysed for the product barcode and this parcel's seal QR; missing evidence is REVIEW, never FAIL.
- **Case resolution:** hold, then 3 tries by the stage owner, then a reviewer. Reviewer decisions always carry a reason and are ledger events. A reviewer override marks failed checks as overridden; they stay on record. A re-sealed parcel voids the old seal. Buyers may override a flagged parcel with a recorded reason: the AI flags, people decide.
- **Laptop vs phones:** the laptop uses `http://localhost:3012` (secure context, no certificate); phones use the HTTPS port.
- **Barcode reading is layered and never model-guessed.** Order: barcode decode, OCR of the printed digits (joined across pieces, with an ISBN-line cross-check to recover noise digits), the phone's own scanner as a hint, then zoomed tiles. All must pass the check digit. A vision model is not used for digits because one invented `9788119153985`, which passes the check by chance. Our own camera timestamp is cropped out before OCR (its digits once looked like a barcode). Registration is two steps: front photo for the name, barcode scan for the identity (the back cover text misleads the model about the title).
- **Payments are a wallet with pay-on-delivery, not a gateway.** The buyer's pre-loaded wallet is checked at the door; there is no card or UPI form. Money moves only through wallet rows, so every balance can be explained.
- **The handover handshake closes the scan-and-take hole.** Courier must open the door session; paying only reserves; the seller is paid only on the courier typing the buyer's one-time code; any timeout, cancel or three wrong codes reverses the reservation. The code never appears in the shared snapshot, only to the buyer.
- **Time rules commit on their own.** An expiry that happens during a request is committed before the request continues, so a later error cannot undo a reversal. A background sweep also applies them.
- **Never wait for the database lock on the event loop.** Doing so deadlocked the server once (a request holding the lock needs the loop to finish). Lock waits happen in worker threads.
- **Notifications are rules, not broadcasts**, each naming recipients and why. Urgent ones beep and vibrate where the browser allows it.
